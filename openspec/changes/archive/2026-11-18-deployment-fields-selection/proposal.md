# Proposal

## Why

`GET /v1/deployments` returns every field of every deployment: about thirty `features` flags, `interface_configs`,
`catalog_properties`, `description`, `intro`, `defaults`, `routes` and more. A client that needs only `id`,
`display_name` and one or two feature flags still downloads and parses all of it, for every model, application,
toolset and router it may use. There is no way to ask for less: the only slim listing, `GET /v1/deployment-names`,
returns two fixed fields (`id`, `object`) and cannot carry anything else.

This change lets the caller name the fields it wants.

## What Changes

- `GET /v1/deployments` accepts an optional query parameter `fields`: a comma-separated list of response field names
  in the wire form (snake_case at the top level), with parentheses for nested fields and `*` for "every key of a map".
  `fields=display_name,features(rate,tokenize)` returns, for each deployment, `id`, `object`, `display_name` and
  `features` holding only `rate` and `tokenize`.
- `id` and `object` are always returned, so the caller can tell a model from an application whatever it selects.
- A name that matches nothing in a deployment is left out of that deployment. Core does not check names against a
  schema: `fields=display_name,descriptio` returns `display_name` and no error. A name only fails when the selection
  text itself is malformed or too large.
- A malformed selection (unbalanced parentheses, an empty name) or one over the limits (1,024 bytes, five
  levels) answers `400`, as an unknown `interface_type` does today. The limits are constants in code.
- The parameter composes with `interface_type`: `interface_type` picks the deployments, `fields` picks what is
  returned for each.
- Without `fields` nothing changes: same rows, same bytes.

A request without `fields` is answered as before. A request that already sends a `fields` parameter for some other
reason is now read as a selection: it gets fewer members per deployment, or `400` when the text is not a selection.

Out of scope:

- `GET /v1/deployments/{id}`, `GET /openai/deployments`, `GET /openai/models` and `GET /v1/deployment-names` do not
  take `fields`. The selection logic is a small standalone piece, so adding it to `/v1/deployments/{id}` later is a
  one-line call; that is a separate decision.
- Checking names against the response schema, or any other feedback on an unknown name.
- Skipping the work that builds a field Core then drops (alias views, application schema resolution, storage
  listing). `fields` shrinks the response and the client's parse work only.
- A GraphQL endpoint, query documents, aliases, arguments or fragments.
- Settings for the limits.
- Baseline specs for the rest of the listing (`interface_type`, access rules, aliases); the new capability states
  only what `fields` adds.

## Capabilities

### New Capabilities
- `deployment-listing`: what `GET /v1/deployments` returns and how a caller narrows it. This change adds the
  requirements for the `fields` parameter and the unchanged behaviour without it.

### Modified Capabilities
(none)

`deployment-interfaces-config`, `deployment-aliases` and `router-deployment` mention `GET /v1/deployments` in
scenarios about what the listing contains. Those scenarios stay true, because they send no `fields`.

## Impact

Motivated by the wish for a lighter `GET /v1/deployments` for clients that need a few fields of many deployments
(discussion in the exploration that preceded this change; no issue or design document yet).

Code: `DeploymentController.listDeployments`, a new `FieldSelection` helper in `server/.../util`,
`OpenApiDescriptions` (the parameter text) and the `@ApiParameter` on `listDeployments`. Tests: a new
`FieldSelectionTest`, assertions in `DeploymentApiTest`. Docs: the generated `docs/open_api_core.yaml` carries the
parameter (regenerated by CI, never hand-edited); no `docs/*.md` describes `GET /v1/deployments`, so none changes.
No new dependency, no setting, no migration. A request without `fields` takes one extra `getParam` call.
