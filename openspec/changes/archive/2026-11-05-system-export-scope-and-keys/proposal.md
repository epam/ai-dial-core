# Proposal

## Why

The system export (`POST /v1/admin/system-export`, #2116) always streams both the `public` and `platform` buckets and
never exports `encryption_keys`. Two follow-ups came out of using it:

- An operator who only needs the admin configuration (`platform`) still downloads, and locks, the much larger `public`
  bucket. Today there is no way to choose.
- The content encryption keys (CEKs) have to be copied out of band, because the first design assumed a CEK is plaintext
  and so unsafe to put in an archive. That holds only when KMS is off: with a KMS provider the CEK blob is wrapped by
  the KMS key and is useless without access to that key. The manual copy is a step that is easy to forget, and an
  archive without its CEKs cannot be read back.

## What Changes

- `POST /v1/admin/system-export` takes an optional query parameter `scope`: a comma-separated list of the buckets to
  export, `public` and `platform`, case-insensitive. Without it the export covers every exportable bucket, as today.
  An empty value, an empty element or an unknown name is answered `400`, before any lock is taken and before the archive
  starts. The archive holds, and the export locks, only the selected buckets.
- When a KMS provider is configured (`toolsets.security.kms.provider` is `aws`, `azure` or `gcp`), the export
  includes the `encryption_keys` blobs of the selected buckets, such as `platform/encryption_keys/cek`. When KMS is off,
  `encryption_keys` stays excluded, because the CEK is stored in plaintext then. `credentials` stays excluded in both
  cases.
- The manifest is unchanged.
- Documentation: `docs/admin-system-export.md` explains the parameter and that the archive restores only where the same
  KMS key is reachable. The controller annotation documents the parameter (`docs/open_api_core.yaml` is generated by CI).
- This reverses one decision of the original design: "Including CEKs: rejected" in
  `docs/notes/public-platform-bucket-export.before-shortening.md`. The reason given there was that a CEK is only valid
  with the same KMS key. That is a restore constraint, not a confidentiality one, so it is now documented instead of
  avoided.

**BREAKING**: none. A request without `scope` behaves as before, except that `encryption_keys` blobs now appear in the
archive when KMS is on. The endpoint is a preview (`x-preview`).

Out of scope:

- `public/credentials` and `platform/credentials` stay excluded (the open question in the same note).
- Importing an archive. How an importer decides which buckets to replace is for its own change.
- Verifying that a CEK blob is KMS-wrapped before exporting it. The setting is trusted. A blob written before a switch
  from `unencrypted` to a KMS provider, or one not yet synced from the write queue, can still be a plaintext CEK. A
  provider switch already invalidates existing encrypted values, so it is an operator event.
- An opt-out for including CEKs when KMS is on.
- Exporting user buckets.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `system-export`: adds the `scope` parameter requirement; changes "Archive layout" (the buckets in the archive are the
  selected ones), "What is left out" (`encryption_keys` is exported when KMS is on) and "Buckets are locked while
  exporting" (the selected buckets are locked, not always both).

## Impact

- Motivation: https://github.com/epam/ai-dial-core/issues/2116 (system export). This change covers its two follow-ups:
  exporting `encryption_keys` when KMS is on, and choosing the buckets. Importing and the credentials question stay open.
- Code: `AdminSystemExportController` (parse and validate `scope`, parameter annotation), `AdminSystemExportService`
  (selected buckets, the encryption-keys rule), `AiDial` (pass whether KMS is on to the service), `KmsSettings` and
  `KeyManagementServiceFactory` (one shared rule for "KMS is on").
- API: one optional query parameter on a preview endpoint, one new `400`.
- Operations: with KMS on, an archive now holds the wrapped CEKs, so it can be restored only into an environment that can
  use the same KMS key. Anyone with the archive and permission to decrypt with that key can read the secrets, which is
  the same exposure as the live bucket.
- Settings: none new.
