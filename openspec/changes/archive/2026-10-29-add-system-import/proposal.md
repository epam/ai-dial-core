# Proposal

## Why

`POST /v1/admin/system-export` (#2116, merged in #2139) writes the `public` and `platform` buckets to one ZIP. There is no way
back. Today an operator has to re-import by hand: stop writers, clear Redis, wipe the buckets, upload every blob with the
headers and user metadata from its sidecar, then restart Core. Every step is easy to get wrong, and a wrong step does not
fail loudly: the imported blobs are masked by cached copies for up to 30 days, or overwritten by queued writes within
minutes. Issue #2116 left the system import to be designed separately. This change is that system import.

## What Changes

- New admin-only endpoint `POST /v1/admin/system-import` (`x-preview`) that takes the ZIP produced by `/v1/admin/system-export` as the
  request body and replaces the content of `public/` and `platform/` with it. `encryption_keys/` is never touched.
- The upload is streamed into a staging prefix `.dial-system-import-tmp/{timestamp}/{importId}/` in blob storage and validated
  while it streams. Nothing is destroyed until the whole archive has been received and found valid.
- Then, under the two bucket locks: wipe both buckets, promote the staged blobs with server-side copies, drop the queued
  and cached Redis entries of both buckets, and rebuild the merged config on the importing pod.
- The response is `200` with a progress line every 15 seconds while the replace runs and a final status line (newline-delimited
  JSON). A failure after the head is
  sent resets the connection, as export does.
- New `ResourceService` method that drops the queued and cached entries of given bucket locations (no blob I/O).
- New `BlobStorage` write path that stores a blob with its full content metadata (type, encoding, disposition,
  language, cache control) and user metadata, streaming, using multipart upload above the part size.
- The temp-folder sweeper in `ResourceService.cleanupTempFolder` is extracted into a reusable class. A second instance
  reclaims abandoned staging prefixes after 24 hours. System import also deletes its own staging in the background after the
  response.
- New `adminSystemImport` settings with code defaults: `stallTimeout` (no bytes from the client for this long fails the upload),
  and `progressInterval`. There are no limits on entry
  count or archive size.
- `InputStreamAdapter` gets an optional read timeout, default none.
- Docs: `docs/admin-system-import.md`, the README settings table, and `docs/admin-system-export.md` (a pointer to system import).

## Capabilities

### New Capabilities
- `system-import`: what `POST /v1/admin/system-import` accepts, rejects and does to the buckets, Redis and the config, and what
  it answers.

### Modified Capabilities
None. The archive that system import reads, its layout and what export leaves out, is specified by the existing
`system-export` capability, which this change relies on and does not modify.

## Impact

- **Motivation.** #2116 ("Importing an archive will be designed separately"). This change is that system import. It covers:
  staging in blob storage, validation before the wipe, treating the archive as untrusted, invalidation after promote,
  rebuild under the lock, the `.dial-system-import-tmp/` prefix. It leaves out, by decision: a flush of the write-back queue
  (declined for export too), a Redis lease with heartbeat and a renewed bucket lock (#2169 owns renewal), cluster-wide
  invalidation of the CEK cache, a force flag, and a job with status polling.
- **Code.** Cited as `path:line` on `development`; details in `design.md`.
  - New: `AdminSystemImportController`, `AdminSystemImportService`, the temp-folder cleaner class, and tests.
  - Changed: `ControllerSelector.java:529` and `RouteTemplate.java:189-191` (route), `AiDial.java:415-433` and
    `Proxy.java:212-213` (wiring and settings), `ResourceService.java:791-845` (sweeper moves into the new class, same
    behaviour for `.dial-tmp`; new method that drops queued and cached entries by bucket, next to `:1307`),
    `BlobStorage.java:153-222` (new write path next to `store` and `copy`), `MergedConfigStore.java:648-660` (a sibling of
    `rebuildNow()` that does not take the bucket locks again) and
    `InputStreamAdapter.java:63-111` (an optional read timeout), `AdminSystemExportService.java:54-56` (the excluded groups become
    package-private so system import shares them).
  - Docs: `README.md:345-352`, `docs/admin-system-export.md`, new `docs/admin-system-import.md`. `docs/open_api_core.yaml` is
    generated by CI from the controller annotations and is not edited.
- **Delivery.** One change, planned as one PR. Tasks are grouped so the storage groups (1 to 4) can land first as their
  own change if review size asks for it; the endpoint group depends on them. This change does not depend on #2169: it uses
  the default 5-minute lock period inside a maintenance window, and system import can adopt lock renewal when #2169 lands.
- **Operators.**
  - The `credentials/` blobs under both buckets are wiped, because export never carries them. Global and
    application-level OAuth sign-ins for toolsets and external services have to be redone after a system import.
  - Other pods keep their old in-memory config for up to `config.reload` (60 s by default) after a system import. They rebuild
    on their own, under the bucket locks.
  - The CEKs are not in the archive. Before importing into another environment, place the source's
    `public/encryption_keys/cek` and `platform/encryption_keys/cek` (the ones that exist; an environment that never stored a
    secret has none) in the target, and roll-restart the pods, as for any out-of-band CEK change. Core does not check this. If
    it is forgotten on an archive with secrets, the rebuild creates a wrong key and the imported secrets do not decrypt until
    the right key replaces it; nothing is lost, and the system import can be run again.
  - A failure in the replace phase (wipe, promote, invalidate, rebuild) can leave the buckets partly imported. The system import
    is repeatable: run the same archive again. A failure in the stage phase (upload and validation) leaves them untouched.
  - Run a system import in a maintenance window with all admin work stopped. The replace phase holds both bucket locks for
    the default lock period of 5 minutes and does not renew them. A replace longer than that lets the locks lapse, so no
    writer, second system import or export may run until the system import has answered. If the pod dies, the locks free
    themselves after at most 5 minutes.
- **Out of scope.** Lock renewal (#2169) and a configurable lock period; limits on entry count or archive size; flushing queued writes before export; signalling
  other pods; invalidating the per-pod CEK cache; checking that the target holds the source's CEKs; `Users/*` and
  `Keys/*`; entities defined only in the local `aidial.config.json`.
- **Cost per request.** None. Chat, embedding and resource traffic do not touch the new code. The only shared change is
  the extracted sweeper, which still runs once a day for `.dial-tmp`.
